# Clarify Code

## Goal

코드의 동작을 바꾸지 않고 이해병목을 줄인다. 이름 개선, 주석, 리팩터링을 병목에 맞게 함께 활용하되 필요한 만큼만 적용한다.

## When to Use

- 코드가 복잡하거나 읽기 어렵다는 요청
- 책임 분리, 함수 추출, 이름 개선 여부를 판단하는 요청
- 동작을 설명하는 주석보다 의도를 드러내는 주석이 필요한 요청

## When NOT to Use

- 기능 추가나 동작 변경이 주목적인 작업
- 성능 최적화나 정확성 중심 코드 리뷰만 요청한 작업
- 사용자 문서의 가독성 개선 작업

## Instructions

### Comments

- 코드가 무엇을 하는지 반복하지 말고, 왜 필요한지 설명한다.
- 정책, 예외 허용 이유, 처리 순서, 비직관적 제약만 기록한다.
- 코드 변경과 함께 낡을 가능성이 큰 주석은 쓰지 않는다.
- 한 블록의 의도는 한 문장으로 적는다.
- 저장소의 언어와 용어 규칙을 따른다.

좋은 예:

```python
# 제외 파일은 진단용으로 남기되, 지원 파일이 있으면 적재를 계속한다.
```

나쁜 예:

```python
# 제외 파일이 있으면 로그를 남긴다.
```

### Refactoring

- 함수 추출은 독립된 책임, 재사용되는 로직, 또는 이름 붙이면 본문이 명확해지는 개념에만 사용한다.
- 한 줄을 감싸는 함수라도 형식 간 대칭성이 탐색 비용을 낮추면 허용한다.
- 단순히 줄 수를 줄이기 위한 helper, 한 구현만 있는 추상화, 미래용 확장점은 만들지 않는다.
- 호출자가 구현을 찾아 여러 파일이나 함수를 왕복하게 만들면 추출하지 않는다.
- 주석과 함수 이름이 같은 설명을 중복하면 하나만 남긴다.
- 오류 처리, 검증, 관측 가능성을 가독성 명목으로 제거하지 않는다.

### Communication

변경 전에는 병목과 적용할 해법들을 짧게 알린다. 변경 후에는 수정한 파일, 동작 보존 근거, 실행한 검증을 보고한다. 변경이 불필요하면 그 이유와 복잡해질 조건만 설명한다.

## Workflow: Resolve Understanding Bottleneck

### Arguments from Context

- 대상 코드와 호출 경로
- 사용자가 분석만 원하는지, 코드 변경까지 원하는지
- 저장소의 언어, 스타일, 테스트 규칙

### Procedure

1. 대상 코드를 끝까지 읽고 호출부와 관련 테스트를 확인한다.
2. 이해병목을 구체적으로 지목한다.
   - 한 함수에 섞인 서로 다른 책임
   - 이름만으로 드러나지 않는 정책, 이유, 불변조건
   - 긴 조건식, 중첩 분기, 서로 다른 추상화 수준
   - 같은 개념의 중복 표현
3. 각 병목에 필요한 해법을 조합한다. 아래 항목은 배타적 선택지가 아니다.
   - 이름이 문제면 변수나 함수 이름을 개선한다.
   - 이유나 정책이 숨었으면 짧은 주석을 추가한다.
   - 독립된 책임이나 이름 붙일 개념이 있으면 함수를 추출한다.
   - 구조 자체가 문제면 제어 흐름을 재구성한다.
   - 이미 명확한 부분은 유지한다.
4. 동작과 공개 API를 보존하는 최소 변경을 적용한다.
5. 가장 가까운 관련 테스트를 실행하고 diff에서 불필요한 변경을 제거한다.

### Validation

- 변경 전후의 동작과 공개 API가 같다.
- 주석이 코드의 표현을 반복하지 않는다.
- 추출된 함수가 독립된 개념을 이름으로 드러낸다.
- 관련 테스트와 diff 검사가 통과한다.

## Constraints

- 사용자가 분석만 요청하면 코드를 수정하지 않는다.
- 기능 추가, 성능 최적화, 대규모 설계 변경으로 범위를 넓히지 않는다.
- 사용자 변경과 무관한 diff를 되돌리거나 덮어쓰지 않는다.
