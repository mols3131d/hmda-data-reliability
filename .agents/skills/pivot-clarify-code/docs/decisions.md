# Clarify Code

## Existence

코드는 동작이 맞아도 이해하기 어려울 수 있다. 이름과 구조만으로 목적이 드러나지 않거나, 호출자가 알아야 할 제약이 숨겨져 있거나, 구현 이유와 책임 경계가 복원되지 않으면 변경할 때마다 같은 맥락을 다시 조사해야 한다.

`pivot-clarify-code`는 이런 **코드 이해 부채**를 줄이기 위해 존재한다.

이 스킬의 목적은 코드를 전반적으로 더 좋게 만드는 것이 아니다. 기존 동작을 보존하면서, 잘못 이해했을 때 비용이 큰 읽기 병목을 해소해 호출자는 사용 의미를, 유지보수자는 의도와 제약을 더 쉽게 복원할 수 있게 한다.

## Essence

- **동작을 보존한다.** 기능, 공개 계약, 성능 목표나 architecture를 clarification 명목으로 바꾸지 않는다.
- **가장 중요한 병목 하나를 먼저 해소한다.** 전면 정리나 미관 개선보다 오해가 실제 misuse나 잘못된 변경으로 이어질 지점을 우선한다.
- **가장 작은 안전한 변경을 선택한다.** 이름과 구조로 충분하면 설명을 늘리지 않고, 설명으로 충분하면 abstraction을 늘리지 않는다.
- **설명은 필요한 의미만 가까이에 둔다.** 호출 의미는 API 가까이, 구현 이유는 코드 가까이, 넓은 정책은 canonical owner에 둔다.
- **기존 근거를 활용한다.** caller, 관련 test와 현재 동작을 읽어 의미와 경계를 복원하되, test를 요구사항의 최종 근거로 취급하지 않는다.
- **범위를 지킨다.** correctness review, architecture redesign, repository navigation, 포괄적 documentation은 주된 문제가 되면 별도 작업으로 분리한다.
- **병목이 해소되면 멈춘다.** 추가로 정리할 수 있다는 이유만으로 작업을 확장하지 않는다.

새 규칙이나 기능을 추가할 때는 이 원칙을 더 잘 수행하게 하는지 확인한다. 스킬의 책임을 넓히거나 별도의 품질 작업을 흡수한다면 추가하지 않는다.
