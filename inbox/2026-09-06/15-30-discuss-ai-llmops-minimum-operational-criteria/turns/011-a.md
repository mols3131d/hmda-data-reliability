## Response

B의 T4 refinement를 수용한다. `control expectation`을 모든 retained case에 복제하는 것은 최소가 아니다.

최소 ownership은 다음처럼 분리한다.

```text
Case Definition
  case identity + replayable input + quality-basis reference

Quality Basis Validation
  rubric/material expectation
  + reproducible negative/positive control discrimination proof
```

Controls가 generic rubric semantics를 검증하면 quality basis 쪽에 한 번 보존하면 된다. 반대로 Q1의 동일 canonical input에서 한 material assertion만 바꾼 paired output처럼 **case-specific context가 있어야 판별 경계를 검증할 수 있을 때만** 그 control recipe를 Q1 dependency로 승격한다.

`Versioned`도 별도 registry나 `v1` field를 무조건 요구하지 않는다. Stable logical ID와 tracked content/project revision으로 어떤 definition이 사용됐는지 재구성 가능하면 첫 최소 proof에는 충분하다. 중요한 것은 baseline과 candidate가 같은 material input/expectation을 사용했다는 것을 검증할 수 있다는 점이다.

## Position

이제 최초 proof와 ongoing operation을 구분해야 한다.

대표 case 하나로 closed loop를 한 번 끝까지 실행하면 **LLMOps mechanism이 작동한다는 readiness proof**는 된다. 하지만 이후 prompt/model/config/review semantics가 바뀌는데 retained case를 다시 적용하지 않아도 계속 “정상 운영”이라고 한다면 `Evaluate and Regress`는 과거 이벤트일 뿐 운영 규율이 아니다.

따라서 ongoing minimum에는 **change-triggered re-evaluation**이 필요하다.

## Proposal

다음 조건을 만족하는 candidate를 사람이 수용하려 할 때 retained case comparison을 다시 수행한다.

> 변경이 Review AI의 material output 또는 그 quality interpretation에 영향을 줄 수 있고, 그 candidate를 실제 사용 상태로 받아들이려는 경우.

예시는 다음과 같다.

- prompt instruction/template identity 또는 material prompt content 변경
- model 또는 output-affecting runtime parameter 변경
- canonical input projection 변경
- review output contract/semantics 변경
- review orchestration/application revision 중 실제 model input/output handling을 바꾸는 변경
- rubric/material quality expectation 변경

반대로 다음에는 quality live compare를 강제하지 않는다.

- 문서만 변경
- review behavior와 무관한 refactor
- deterministic test/formatting 변경
- artifact path spelling처럼 output semantics에 영향이 없는 변경

## Minimum Trigger Contract

운영 trigger는 CI workflow나 scheduler일 필요가 없다. 최소 contract는 다음이면 된다.

```text
applicable output-affecting candidate
→ current retained case/rubric resolve
→ candidate replay/compare
→ durable human decision
→ candidate accept/reject/no-change
```

Manual checklist나 release/change review에서 실행해도 된다. 중요한 것은 **candidate를 수용한 뒤가 아니라 수용 판단에 evaluation evidence가 들어가는 것**이다.

Rubric 자체가 materially 변경되면 candidate comparison 전에 해당 rubric version의 bounded control discrimination을 다시 검증한다. Rubric이 그대로라면 controls를 매 candidate마다 재실행할 필요는 없다.

## Strongest Counterargument

모델 자체는 repository 밖에서 provider alias나 hosted model behavior가 바뀔 수 있다. 그러면 repository change가 없어도 output이 달라질 수 있으므로 “코드 변경 때만 re-evaluate”는 완전한 운영 trigger가 아니다.

하지만 이 문제를 해결하기 위해 polling, scheduled online eval 또는 continuous monitoring을 최소 기준에 넣으면 현재 MVP를 넘는다. 첫 최소 운영 규율은 **통제 가능한 candidate acceptance event**를 trigger로 삼고, 외부 provider drift 감시는 별도 확장으로 남기는 것이 적절하다.

## Evidence

- [`docs/VISION.md`](../../../../docs/VISION.md)는 reproducible case와 expected outcome으로 변경 전후를 비교하는 `Evaluate and Regress`를 LLMOps feedback loop의 핵심으로 둔다. 한 번만 실행하고 이후 output-affecting 변경을 통과시키는 것은 이 운영 규율을 유지하지 못한다.
- 현재 CI Lite는 deterministic source/test admission을 담당하고 실제 provider invocation을 기본 실행하지 않는다. 따라서 minimum re-evaluation trigger를 CI/live automation과 동일시하면 현재 boundary를 불필요하게 확대한다.
- [`docs/mvp.md`](../../../../docs/mvp.md)는 deterministic Agentic proof와 opt-in Live Agentic proof를 구분한다. Ongoing quality gate도 자동 live CI가 아니라 명시적 candidate comparison evidence로 시작할 수 있다.
