## Position

첫 closed-loop proof에 **실제 traced model invocation의 `FAIL`을 필수로 요구하는 데에는 반대한다.** 필요한 비자명성은 evaluator가 material quality violation을 구별할 수 있다는 proof이지, 현재 provider/model이 우연히 그 violation을 실제로 발생시켜야 한다는 조건이 아니다.

최소 기준은 다음 두 층을 분리하는 편이 더 정확하다.

1. **Evaluator discrimination proof** - 같은 versioned case/rubric이 명시적인 negative control을 `FAIL`, compliant control을 `PASS`로 구별한다.
2. **Closed-loop proof** - 실제 traced baseline/candidate invocation을 그 고정된 case/rubric으로 평가하고 compare하여 human decision에 소비한다.

따라서 실제 traced run이 `PASS → PASS → no-change`여도, rubric이 별도의 bounded negative control에서 실제 `FAIL`을 검출했다면 loop proof는 비어 있지 않다.

## Evidence

현재 프로젝트의 live harness는 명시적으로 **one real provider proof**를 수행하며, 고정 `null_spike` material을 실제 provider에 보내 provenance와 accepted/rejected 상태를 검증한다. 이 harness의 목적은 provider/runtime wiring proof이지 특정 semantic failure를 생산하는 것이다.

반면 task-quality rubric은 아직 구현되지 않았다. 여기서 최초 운영 기준을 “실제 model failure가 나올 때까지 실행”으로 정의하면 proof의 성공 여부가 evaluator/feedback-loop 구현이 아니라 모델의 우연한 실패 발생에 종속된다. 특히 현재처럼 bounded advisory review이고 prompt가 이미 uncertainty를 요구하는 경우, 좋은 모델일수록 첫 대표 case에서 계속 PASS할 수 있다.

또한 실제 traced `FAIL`을 만들기 위해 의도적으로 prompt/model/config를 악화시키면 더 큰 문제가 생긴다. 그 run은 자연스럽게 발견된 operational failure가 아니라 **synthetic perturbation을 provider를 통해 실행한 negative control**일 뿐이다. 이 경우 “실제 invocation이었다”는 사실은 discrimination proof를 더 end-to-end하게 만들지만, 실제 production-like model failure라는 추가 의미는 없다.

## Counterexample

A의 조건을 그대로 필수화하면 다음 구현은 loop가 정상이어도 완료할 수 없다.

```text
Q1 + rubric v1
negative control = unsupported root-cause assertion → FAIL
positive control = explicit uncertainty → PASS
baseline traced run = PASS
candidate delta = prompt wording cleanup
candidate traced replay = PASS
same rubric compare = PASS → PASS
human decision = no-change
Q1 retained
```

이 상태는 evaluator가 실제 material violation을 구별하고, 실제 model output 두 개를 같은 기준으로 비교하고, 판단까지 소비했다. 그런데 provider가 Q1에서 실패하지 않았다는 이유만으로 LLMOps 자체를 “미작동”으로 분류하는 것은 품질 결과와 운영 capability를 혼동한다.

반대로 실제 traced `FAIL` 하나만 요구해도 충분하지 않다. Candidate output을 본 뒤 rubric을 수정해 baseline만 FAIL시키거나, baseline/candidate 사이에 식별 가능한 prompt/model/config/project delta가 없어도 형식상 `FAIL → FAIL → reject`를 만들 수 있다. 그러므로 비자명성의 핵심은 failure의 물리적 출처보다 **고정된 판별 기준과 비교 가능한 변화**다.

## Proposal

T2의 최소 조건을 다음처럼 둔다.

> 최초 quality case에는 candidate 실행 전에 version이 고정된 rubric과 최소 한 쌍의 bounded controls가 있어야 하며, rubric은 material violation control을 `FAIL`, compliant control을 `PASS`로 판별해야 한다. 이후 실제 traced baseline/candidate output을 같은 rubric으로 평가·비교해 human decision에 소비한다.

추가 guardrail은 두 개면 충분하다.

- **Precommit** - case/rubric version은 candidate output을 보기 전에 고정한다.
- **Identifiable candidate delta** - baseline과 candidate 사이에는 prompt identity, model/config 또는 project revision 중 이번 변경 판단의 원인이 되는 delta가 추적 가능해야 한다.

실제 traced `FAIL`이 자연스럽게 관찰되면 가장 좋은 representative failure가 되고 retained regression case로 승격하면 된다. 그러나 그것을 첫 loop의 필수 선행조건으로 만들지는 않는다.

그리고 이 proof를 delegation-readiness와 분리해야 한다. 한 case의 `PASS → PASS` 또는 `FAIL → PASS`는 **feedback mechanism이 닫혔다는 최소 proof**일 뿐, 더 넓은 AI 위임에 필요한 품질의 일관성을 증명하지 않는다. Delegation 확대에는 이후 case coverage와 반복 평가가 별도로 필요하다.
