## Position

B의 핵심 반론을 수용한다. `Evaluatable`은 단순 contract regression이 아니라 **task usefulness까지 검증하는 `Quality-evaluable`**이어야 하고, `Decision-connected`는 evidence가 실제 판단에 쓰였음을 확인하는 **`Feedback-consumed`**가 더 정확하다.

이번 turn의 새 주장은 하나다.

> **LLMOps 최소 완료 기준은 네 capability가 각각 존재하는 것이 아니라, 대표 case 하나에서 네 gate가 실제로 한 번 끝까지 연결된 proof가 있어야 한다.**

그렇지 않으면 trace, eval, replay, decision artifact가 모두 따로 존재해도 feedback loop가 정상 작동했다고 증명할 수 없다.

## Evidence

- [`docs/VISION.md`](../../../../docs/VISION.md)의 loop는 `Run + Outcome → Trace + Version → Evaluate + Compare → Boundary Review → Delegation Policy`처럼 연결된 흐름이다. 개별 기능 inventory가 성공 기준은 아니다.
- [`docs/mvp.md`](../../../../docs/mvp.md) 역시 feature count보다 하나의 완결된 proof를 acceptance 기준으로 둔다.
- B가 지적했듯 현재 structured validator는 canonical fact와 evidence linkage를 검증하지만 review의 실질적 유용성은 보장하지 않는다. 따라서 quality expectation이 없는 regression은 이 loop의 핵심 증거가 될 수 없다.
- 현재 repository의 replay는 stored canonical input과 recorded revision을 이용한 prompt/provenance 재구성과 deterministic fixture 재실행에는 강하지만, task-quality failure를 다시 실행해 baseline/candidate usefulness를 비교하는 proof와는 구분해야 한다.

## Response

B의 `Feedback-consumed`에는 동의하되 pass 조건을 조금 더 좁힌다.

단순히 eval 링크를 사람이 읽었다는 기록은 부족하다. 최소 proof에서는 **같은 versioned case의 baseline/candidate 또는 failure replay 결과를 근거로 `accept / reject / no-change` 중 하나를 명시적으로 결정**해야 한다. Delegation boundary 자체를 바꾸거나 production policy를 갱신할 필요는 없다. 변경하지 않기로 한 판단도 충분하다.

반대로 `baseline/candidate compare`를 별도 다섯 번째 gate로 만들 필요는 없다. 비교는 `Quality-evaluable`의 필수 pass test로 포함하면 된다. Gate 수를 늘리면 실제 loop보다 taxonomy가 커진다.

## Change

첫 A turn의 `Evaluatable`과 `Decision-connected` 표현을 수정한다.

| Gate | Revised minimum pass test |
| --- | --- |
| **Traceable** | 대표 live run의 evidence/canonical input, prompt identity, model/config, project revision, output/status, latency와 가능한 usage를 다시 식별할 수 있다. |
| **Quality-evaluable** | versioned case에 structured contract와 분리된 task-quality 기대 조건이 최소 하나 있고, 같은 case에서 baseline과 실제 candidate를 비교해 usefulness regression 여부를 판단할 수 있다. |
| **Replayable** | 실제 실패 또는 의도적으로 만든 대표 edge case 하나를 versioned regression case로 남겨 이후 다시 실행하고 같은 quality 기준으로 비교할 수 있다. |
| **Feedback-consumed** | 위 eval/replay evidence를 근거로 실제 human `accept / reject / no-change` 판단 하나가 남고, 해당 case가 다음 candidate에서도 재사용된다. |

## Proposal

“LLMOps가 정상 작동한다”의 최소 증명은 다음 한 사이클이면 충분하다.

```text
Versioned quality case
→ baseline live run + trace
→ candidate run + same quality check
→ compare
→ representative failure/edge replay
→ human accept/reject/no-change
→ case retained for next candidate
```

여기서 task-quality rubric은 처음에는 **human-authored binary expectation 하나**여도 된다. 예를 들어 `null_spike` case에서 의도적으로 심은 중요한 omission 또는 uncertainty를 review가 실제로 드러내는지를 본다. 자동 judge, aggregate score, dashboard는 필요 없다.

현재 가장 작은 다음 작업은 baseline만 저장하는 데서 끝나면 아직 loop proof가 아니다. **versioned quality case 하나를 정의하고, current baseline과 실제 candidate 하나를 같은 rubric으로 비교해 human decision까지 남기는 것**이 최초의 end-to-end LLMOps proof가 된다.
