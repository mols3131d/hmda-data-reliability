## Response

A의 ownership 분리는 대체로 맞다. 특히 authored case definition을 generated invocation evidence와 분리해야 한다는 결론에는 동의한다. 과거 invocation만 보존하면 다음 candidate에서 **같은 input과 같은 quality expectation을 재적용했는지** 검증할 수 없기 때문이다.

다만 `control expectation`을 각 retained case definition의 영구 필수 필드로 넣는 것은 최소 기준을 한 단계 과하게 만든다.

T2에서 bounded negative/positive controls가 필요한 이유는 **rubric/evaluator가 vacuous하지 않다는 것을 검증**하기 위해서였다. 이 검증 대상은 개별 model invocation이 아니라 quality basis의 discrimination capability다. 따라서 control fixture와 그 PASS/FAIL evidence는 case 자체의 semantic identity와 동일한 수명을 가질 필요가 없다.

## Boundary

최소 retained case가 다음 candidate에서도 같은 regression question을 재현하려면 필수인 것은 세 가지다.

| Required | Why |
| --- | --- |
| stable case identity | 이전 decision과 다음 replay가 같은 case임을 연결한다. |
| replayable input definition | 같은 incident/evidence boundary를 다시 만든다. |
| versioned quality basis | 같은 material expectation으로 다시 판정한다. |

반면 bounded controls는 **quality basis가 처음 도입되거나 materially 변경될 때** 그 basis가 `FAIL`과 `PASS`를 구별할 수 있음을 증명하면 된다.

```text
case Q1
  input recipe
  rubric R1

rubric R1 validation evidence
  negative control -> FAIL
  positive control -> PASS
```

Q1을 candidate N, N+1, N+2에 replay할 때마다 control expectation을 Q1 definition 안에 중복 보존하거나 controls를 다시 실행할 필요는 없다. R1이 그대로라면 이미 versioned validation evidence를 참조할 수 있다.

## Counterexample

다음 두 case가 같은 rubric을 공유한다고 하자.

```text
Q1: root-cause uncertainty on null_spike
Q2: unsupported causal claim on schema drift
R1: material unsupported causal claim => FAIL
```

각 case artifact에 동일한 positive/negative control을 필수로 내장하면 control ownership이 case에 중복된다. 더 나쁜 경우 control wording을 고치기 위해 Q1/Q2 case version까지 바뀌어, 실제 regression input/expectation은 그대로인데 case identity history가 불필요하게 흔들린다.

반대로 controls를 아무 durable evidence 없이 일회성으로만 실행하고 버리는 것도 부족하다. 그러면 나중에 `R1`이 non-vacuous하다는 T2 proof를 재검증할 수 없다.

따라서 controls는 **retained되어야 하지만 case definition에 반드시 내장될 필요는 없다.** 최소 ownership은 `quality basis validation evidence`로 두는 편이 정확하다.

## Proposal

`Same Case Retained`의 최소 pass condition을 다음처럼 좁힌다.

> Stable case identity가 replayable input definition과 versioned quality basis를 가리키고, 그 quality basis에는 bounded positive/negative control discrimination을 재구성할 durable validation evidence가 존재한다.

여기서 authored artifact가 하나의 파일인지 여러 파일인지는 중요하지 않다. 작은 프로젝트에서는 한 tracked fixture에 case와 rubric과 controls를 같이 둘 수도 있다. 중요한 것은 논리적 ownership이다.

```text
Authored Case Definition
  owns: case identity + replayable input + quality-basis reference

Quality Basis / Validation Evidence
  owns: rubric version + material expectation
        + bounded control discrimination proof

Invocation Evidence
  owns: actual run + provenance + output + operations

Decision Evidence
  owns: comparison + change-under-test + human decision
```

추가로 versioning 의미를 분리해야 한다. Input recipe 또는 material expectation이 바뀌면 같은 regression question인지 다시 판단해야 한다. 단순 표현 수정이나 control fixture 정리는 stable `case_id` 자체를 새로 만들 이유가 아니다. 최소 구현에서 필요한 것은 immutable artifact hash 체계가 아니라, **어떤 case/rubric version으로 baseline과 candidate를 평가했는지 durable하게 식별 가능**한 정도다.

## What would prove this wrong

실제 replay에서 bounded controls가 case-specific input semantics에 강하게 결합되어 있어, rubric-level validation evidence만으로는 Q1의 evaluator discrimination을 재구성할 수 없는 사례가 확인된다면 controls를 case definition의 필수 일부로 올려야 한다.

예를 들어 Q1의 negative control이 generic text가 아니라 동일 canonical input에서 오직 한 material assertion만 바꾼 paired output이어야 판정 경계를 검증할 수 있다면, 그 control recipe는 Q1과 함께 versioned되는 편이 맞다. 그래도 핵심은 "모든 case는 control 필드를 가져야 한다"가 아니라 **discrimination proof를 재구성하는 데 필요한 최소 dependency를 versioning한다**는 것이다.
