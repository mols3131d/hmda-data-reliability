## Agreement

A의 네 gate 방향에는 대체로 동의한다. 특히 `Decision-connected`를 없애면 trace와 eval이 있어도 결과가 다음 판단으로 돌아오지 않으므로 **닫힌 loop라고 부르기 어렵다.** Safety를 별도 system invariant로 두고, LLMOps는 그 위임 경계를 검토할 evidence를 제공한다는 분리도 타당하다. Airflow, 별도 LLMOps SaaS, production dashboard, online evaluation, 자동 prompt optimization은 최소 조건이 아니다.

## Weakest Assumption

가장 약한 부분은 `Evaluatable`의 pass test가 **무엇을 평가해야 하는지 충분히 강하지 않다**는 점이다. 현재 [`reliability-agentic-review`](../../../../openspec/specs/reliability-agentic-review/spec.md)의 structured-fact validation은 fabricated evidence, identity mismatch와 deterministic contradiction을 막지만, free-text review가 실제로 유용한지는 의도적으로 acceptance oracle로 판정하지 않는다.

따라서 versioned case와 regression 비교가 존재한다는 사실만으로는 부족하다. 평가 기준이 schema, evidence reference와 canonical fact 보존에만 머물면 **안전한 형식의 무용한 review**도 계속 통과할 수 있다.

## Failure Scenario

모델이 모든 `null_spike`에서 canonical 숫자와 Evidence ID를 정확히 복사하고 항상 “증가가 확인되므로 human review가 필요하다” 정도만 반환한다고 가정한다. `RemediationDraft`의 누락, 중요한 uncertainty 또는 실제 검토 가치가 있는 문제를 전혀 찾지 않아도 structured validation은 accepted가 될 수 있다.

이 상태에서도 다음은 형식적으로 가능하다.

- live invocation provenance 저장
- 같은 structural fixture의 반복 eval과 버전 비교
- schema-invalid 또는 fabricated-evidence 실패 replay
- 결과를 human review 문서에 연결

그러면 A의 네 gate가 모두 있는 것처럼 보이지만, **LLM review가 왜 필요한지에 대한 품질 근거는 없다.** 이것은 호출 성공보다 한 단계 정교한 가짜 완료다.

## Minimum Revision

네 gate 자체를 늘리기보다 pass 조건을 다음처럼 좁히는 편이 작다.

| Gate | B의 최소 조건 |
| --- | --- |
| **Traceable** | A 제안 유지. 중요한 live run의 evidence, prompt/model/config/revision/output을 재식별할 수 있고 MVP가 요구하는 latency와 가능한 usage도 남는다. |
| **Quality-evaluable** | versioned eval case에 **structured safety/contract와 분리된 최소 한 개의 task-quality 기대 조건**이 있어야 한다. 예: 의도적으로 심은 omission이나 uncertainty를 review가 실제로 드러내는지. 자동 scorer는 필요 없고 작은 human-authored binary rubric이면 충분하다. |
| **Replayable** | 실제 실패 또는 의도적으로 만든 대표 edge case 하나를 versioned regression case로 승격해 다시 실행하고 비교할 수 있음을 증명한다. 별도 replay platform은 필요 없다. |
| **Feedback-consumed** | eval/replay 결과가 단순히 “볼 수 있는 상태”가 아니라, 최소 한 번의 명시적 human `accept / reject / no-change` 판단에 실제로 인용되어야 한다. 그 case는 이후 candidate 변경의 eval gate에 남는다. |

마지막 조건은 `Decision-connected`보다 조금 강하지만 더 검증 가능하다. 문서나 dashboard에 링크가 있다는 것과 evidence가 실제 의사결정에 소비됐다는 것은 다르다. 반대로 delegation boundary가 실제로 변경될 필요는 없다. 근거를 보고 **변경하지 않기로 한 결정**도 유효한 feedback이다.

## Current Position

현재 입장은 **A의 네 단계 구조를 유지하되 `Evaluatable`을 `Quality-evaluable`로 강화하고, `Decision-connected`를 실제 소비 증거가 필요한 `Feedback-consumed`로 명확히 해야 한다**는 것이다.

이 프로젝트에서 최소 닫힌 loop는 다음 정도면 충분하다.

```text
Versioned Eval Case
→ LLM Run + Trace
→ Contract/Safety Check + Task Quality Evaluation
→ Baseline/Candidate Compare
→ Failure/Edge Case Regression
→ Human Change/No-change Decision
→ 다음 candidate의 같은 Eval Gate
```

여기에 Langfuse/MLflow, Airflow 통합, 다수 모델 비교, 복잡한 scoring framework 또는 자동 최적화를 추가해야만 LLMOps가 성립한다고 보지는 않는다.
