## Position

내 첫 제안은 다음과 같다.

> **“LLMOps가 정상 작동한다”의 최소 기준은 한 번의 LLM 호출이 성공하거나 structured validation을 통과하는 것이 아니라, 동일한 평가 사례를 다시 실행해 실제 task usefulness를 판단하고, 변경 전후와 실패를 비교한 뒤, 그 근거를 다음 사람의 변경·위임 판단에 사용할 수 있는 작은 feedback loop가 닫혀 있는 상태다.**

최소 gate는 다섯 개로 본다.

| Gate | Minimum pass test | 현재 판단 |
| --- | --- | --- |
| **Traceable** | 중요한 live invocation을 evidence/canonical input, prompt identity, model/config, project revision, output/status와 연결해 다시 식별할 수 있다. latency, attempt와 provider가 제공하는 usage도 같은 evidence에서 확인할 수 있다. | 충족 |
| **Usefulness-evaluable** | 작은 versioned eval case 집합을 같은 조건에서 다시 실행하고, “사람의 review 판단에 실제 도움이 되는가”를 사전에 정한 기준으로 pass/fail 또는 비교할 수 있다. | 미충족 |
| **Change-comparable** | prompt/model/application 변경 후보와 기준 버전을 같은 eval case에 실행해 품질 regression 여부를 비교할 수 있다. | 미충족 |
| **Failure-replayable** | 실제 실패나 중요한 edge case를 보존해 이후 eval case로 재실행할 수 있다. exact model 재현이 불가능하면 버전 차이를 명시한 replay여도 된다. | 부분 충족 |
| **Decision-connected** | eval 결과가 최소한 `keep / reject / needs review` 같은 사람의 변경 판단에 사용되고, delegation boundary 변경은 별도 명시적 인간 결정으로 남는다. | 부분 충족 |

`deterministic validation`은 필수 안전 기반이지만 **task usefulness의 대체물이 아니다.** 현재 validator는 evidence reference, incident identity와 canonical facts의 모순을 잡도록 의도적으로 한정되어 있고 free-text 의미는 acceptance oracle로 쓰지 않는다. 따라서 accepted output도 “구조적으로 안전한 advisory output”일 뿐 “유용한 review”가 자동으로 증명되지는 않는다.

## Evidence

- [`docs/VISION.md`](../../../../docs/VISION.md)는 LLMOps를 `Trace and Version → Evaluate and Regress → Replay Failures → Boundary Review`의 feedback loop로 두고, 실제 평가에서 품질과 효용을 증명한 근거가 delegation boundary 판단으로 이어져야 한다고 명시한다.
- [`docs/mvp.md`](../../../../docs/mvp.md)는 structured contract의 deterministic evaluation과 observable live model proof를 둘 다 요구하면서도 live proof를 deterministic regression과 동일하게 취급하지 않는다.
- [`openspec/specs/reliability-agentic-review/spec.md`](../../../../openspec/specs/reliability-agentic-review/spec.md)는 deterministic validator가 free-text advisory quality를 authoritative하게 평가하지 않도록 제한하고, offline evaluation은 contract/provenance/authority separation 중심으로 정의한다.
- [`scripts/run_agentic_review_live.py`](../../../../scripts/run_agentic_review_live.py)는 실제 호출 결과와 durable provenance, prompt replay consistency를 검증하지만 답변의 실제 유용성을 채점하지 않는다. [`tests/review_ai/test_live_harness.py`](../../../../tests/review_ai/test_live_harness.py)도 이 harness 경계를 검증한다.
- 좁은 repository search에서 task usefulness용 rubric, golden/expected semantic case, baseline-vs-candidate comparator는 확인하지 못했다. 반면 structured validation과 live provenance 관련 구현·테스트는 확인됐다.
- 기존 orchestration 논의는 Airflow가 domain logic을 직접 소유하지 않고 실행 순서와 task state만 조율하는 방향이다. 따라서 이 최소 LLMOps loop를 Airflow나 별도 플랫폼에 억지로 넣는 것은 현재 질문의 필수 조건이 아니다.

## Proposal

가장 작은 usefulness 평가 방식은 **새 플랫폼이나 LLM-as-judge가 아니라, 소수의 versioned case + 사람이 정의한 짧은 rubric**이면 충분하다고 본다.

예를 들어 각 case에서 기존 deterministic contract 검증 뒤 다음 세 항목만 평가한다.

1. **Relevant insight** — 제공된 evidence에서 사람이 판단할 material concern, omission 또는 uncertainty를 하나 이상 제대로 짚는가.
2. **Decision usefulness** — summary/findings가 단순 canonical fact 반복을 넘어 human review에 실제 추가 정보를 주는가.
3. **Recommendation fit** — `support / needs_human_review / insufficient_evidence`가 case의 기대 판단과 부합하는가.

이 세 항목은 처음부터 자동 semantic judge로 만들 필요가 없다. 작은 fixture에 human-authored expected outcome을 두고 deterministic assertion으로 가능한 부분만 검사하며, 애매한 free text는 사람이 짧게 확인하는 방식이 KISS에 맞다.

최소 기준에서 제외할 것은 다음이다.

- Langfuse, MLflow 같은 별도 LLMOps 플랫폼
- online continuous evaluation과 장기 monitoring
- multi-model routing/fallback graph
- 자동 prompt optimization
- LLM-as-judge 자체
- production latency SLO, percentile dashboard, cost budget
- 모든 invocation의 비용 계산; provider가 제공하면 기록하는 수준이면 충분
- Airflow가 LLMOps semantics를 소유하는 구조

내가 B에게 가장 먼저 반박받고 싶은 지점은 세 가지다. **(1)** usefulness eval을 최소 gate로 강제해야 하는가, **(2)** change comparison은 독립 gate인가 아니면 eval의 자연스러운 결과인가, **(3)** failure replay와 decision linkage가 MVP 최소 기준으로 과도한가.
